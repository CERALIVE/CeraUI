## CONVENTIONS

- Stores: Svelte 5 runes only (`$state`, `$derived`, `$effect`) — files named `*.svelte.ts`.
- **REMEMBER-ME STORES A TOKEN, NEVER THE PASSWORD [EXISTS]:** `localStorage.auth` holds the device-issued, individually revocable `auth_token` from a persistent login. `authenticateWithToken()` and reconnect use `auth.login`'s `input.token` branch, never `input.password`. The auth store persists the issued token before publishing successful auth; an unchecked successful login removes a previous credential, and successful token reauthentication without a replacement retains the existing one. `SystemHelper.savePassword` delegates to `createPassword()`, which clears the remembered credential only after the device confirms the password change that revokes all outstanding tokens. `Layout.svelte`'s explicit clear-saved-session action also best-effort calls `revokePersistentToken`, without delaying the local clear. Extend `src/tests/auth-no-plaintext-password.test.ts` for any new credential writer. Device half: [`../backend/AGENTS.md`](../../../backend/AGENTS.md) → A REMEMBER-ME CREDENTIAL IS A REVOCABLE TOKEN; policy: root charter **G3**.
  **THE TAXONOMY IS THE CONTRACT, and it is board-proven.** `rejected` is the ONLY verdict that may delete `localStorage.auth`; `unreachable` — socket-not-ready, RPC error, timeout — must PRESERVE it, because a device that cannot be reached has said nothing about whether the credential is still valid, and deleting it there is how a backend restart turns into a password prompt the operator did not earn. Drill C2 exercised exactly that on a Rock 5B+: a remembered login survived a reload, then a REAL `systemctl restart ceralive` with two reloads inside the outage, `localStorage.auth` unchanged throughout, no password screen, and the session re-authenticated 1972 ms after HTTP returned; the unchecked-remember control ran in the same session and correctly landed on the password screen with the key absent. One browser-observation trap worth knowing before writing a similar test: a reload while HTTP is down moves Chromium to an error document, and CDP `DOMStorage.getDOMStorageItems` then fails `Frame not found for the given storage id` even though origin storage survives — assert through an in-memory `BrowserContext.storageState()` across that window and never persist that credential-bearing state to disk.
  **Residual, recorded by name: the token is device-issued and device-scoped only.** A CLOUD-issued server token that would let one operator credential span devices is a separate design and does not exist; it is registered as an engineering follow-up in [`../../docs/DESIGN-FOLLOWUPS.md`](../../../../docs/DESIGN-FOLLOWUPS.md) rather than implied here.
- **Store ownership (single owner rule) [EXISTS]:** `lib/rpc/subscriptions.svelte.ts` is the SOLE `rpcClient.onMessage` consumer and owns every non-auth reactive/connection getter (`getConfig`, `getStatus`, `getIsConnected`, `getConnectionState`, …). `lib/stores/auth-status.svelte.ts` is the SOLE auth-mutation and remember-me persistence path (`ingestAuth`/`getAuthMessage`/`authenticate`/`authenticateWithToken`/`createPassword`/`revokePersistentToken`/`authStatusStore`). Both login entrypoints return `AuthAttempt` (`ok | rejected | unreachable`); automatic credential invalidation requires server rejection, while socket/RPC/timeout failures preserve it for Retry or explicit clearing. On success persistence settles synchronously before auth state flips, so `Auth.svelte` must not recreate a persistence `$effect` that can lose the write on unmount. The legacy `websocket-store.svelte.ts` wrapper (528 LOC) is FULLY DELETED — do not re-add it or a second `onMessage`/auth-mutation owner. A CI grep gate (`src/tests/deprecated-ws-store-gate.test.ts`) fails the build if the literal module name reappears anywhere in `apps/frontend/src`. `offline-state.svelte.ts`/`pwa-status.svelte` are the one deliberate exception — they read connection state straight off `$lib/rpc/client` (not `subscriptions.svelte`) to stay pre-auth-pure.

- i18n namespace activation [EXISTS]: every namespace is its own lazily-imported chunk, and `lib/i18n/namespace-activation.ts` owns WHEN each one loads. `BOOT_NAMESPACES` — awaited by `main.ts` before `mount()` — is everything FIRST PAINT can read: the auth gate, layout chrome, nav, HUD, toast/notification surfaces, PWA/offline pages, shared dialog chrome, the shell stores that render copy of their own (`async-operation`'s failure toast, `Badge`'s stale marker), AND the default `live` destination's own view. `DESTINATION_NAMESPACES` is the remainder, keyed by `navElements` destination key, resolved by `NavigationRenderer` at the navigation activation point; boot is DERIVED as the complement, so a namespace can never be orphaned. Three rules are load-bearing. **(1)** The default destination boots — deferring `live`/`settings` would defer ~55% of the catalog but splits first paint into two phases (shell, then the operator's primary surface pops in) and breaks "the nav is active ⇒ the view is on screen", which `navigateTo` and every one-shot `page.evaluate` in the e2e suite rely on; that is a product decision, not a bundling one. **(2)** An already-loaded destination renders SYNCHRONOUSLY (`areDestinationNamespacesLoaded`) — gating every navigation behind a promise tick re-introduces the same race for no benefit. **(3)** `prefetchDeferredNamespaces()` runs AFTER mount, non-blocking; it is the latency guarantee, never the correctness one — the activation gate is what stops a view rendering dotted keys. Do NOT "simplify" this back to `ensureAllNamespaces()` in `main.ts`, and do NOT move a namespace into the generator's `EAGER_NAMESPACES` to make it load at boot (that fuses it into the entry chunk — a measured ~400 KB gzip regression). Coverage: `src/tests/i18n-namespace-activation.test.ts`.

- Per-field sync state: `rpc/field-sync-state.svelte.ts` is a lifecycle machine (`idle → pending → applying → applied | failed`) layered ON TOP of the dirty-registry — it does NOT replace it. It composes the existing `markPending` / `onRpcResolved` / `onRpcAppliedReactive` lock contract (so a field locked here is the same lock the ingestion path guards) and adds the phase. Consumers call `beginFieldSync` → `markFieldApplying` → `markFieldApplied(field, result.applied)` / `markFieldFailed(field, authoritative)`; read the phase with `getFieldState(field)` and render `custom/FieldSyncIndicator.svelte` (the InlineSpinner during `applying`). - Config dialogs are LAZY CHUNKS, and a new one must be too [EXISTS]: every dialog mounted by `LiveView`/`NetworkView`/`SettingsView` loads on first open through the registry in `lib/components/dialogs/` — `lazyDialog(() => import('./dialogs/X.svelte'))` in the view's `<script>`, `<LazyDialog dialog={X} bind:open={xOpen} … />` at the mount site. The dialog components themselves are untouched by this; it is a bundling change, and a call site keeps its exact props. It is worth ~91 KiB gzip off the initial route, and under rolldown a dynamic `import()` is the ONLY thing that moves bytes out of the entry chunk (a `manualChunks` name cannot split a statically-reachable module — see `scripts/ci/bundle-report.mjs`). Four rules: **(1)** use the registry, never an inline `{#await import(...)}` at the mount site — `{#await}` re-evaluates, so every re-open would re-fetch, and the fetch-once property is pinned by `lazy-dialog.svelte.test.ts` AND by `tests/e2e/lazy-dialog-chunks.spec.ts`. **(2)** A dialog with a SECOND `bind:` cannot go through `LazyDialog` (a rest-spread cannot carry a binding) — `EncoderDialog` binds `config` as well as `open`, so it mounts through the registry directly with its own one-line `$effect` request edge; copy that shape. **(3)** A dialog that also exports a TYPE splits into a static `import type { … }` (erased at compile — no runtime edge) plus the dynamic import; this is not an API change. **(4)** `LazyDialogFallback` is delayed by `LAZY_DIALOG_FALLBACK_DELAY_MS` (150 ms) and carries NO `data-testid` — rendering it unconditionally would mount and unmount a second bits-ui dialog (portal + focus trap + scroll lock) in front of the real one on every open, and a testid on it could resolve a spec waiting for the real dialog. The federation entries are unaffected: they import their dialogs directly and must stay statically complete.

The operator's codec choice (`localCodec`) IS persisted: `handleSave` writes it to the draft's `codec` → `video_codec` config field (fully wired through `streaming.schema.ts` → `config-schemas.ts` → `streaming.procedure.ts` → `cerastream-backend.ts`). `PreviewCanvas` (#72) stays mounted. Resolution/Framerate are device-mode-aware: `offeredAxes(hardware, pipelineId, pipeline, deviceModes, selectedVideoInput)` (`ValidationAdapter.ts`) intersects `platform ∩ active-source ∩ Tier-2 device modes` (`capabilities.device_modes` from `list-devices`), `framerateOptionsForResolution(axes, resolution)` gates framerate PER selected resolution, and `axisCeiling(axes)` drives the `axis-summary` line (`axis-current` / `axis-device-max` testids) — `axisCeiling` returns the ACHIEVABLE resolution×framerate pair when Tier-2 device modes are present (intersecting the top rung's own modes with the offered framerates, live-correctness-pass Todo #2/#3), never a fictional independent-axes max; `framerateAvailableAt(axes, fps, excludeResolution)` drives the per-option "available at Nx" hint, keyed on the candidate fps. With `device_modes` absent the offering is byte-identical to the coarse path (old-engine fallback). Option lists carry `data-testid="resolution-option"`/`"framerate-option"` with `data-value`, `aria-disabled`, and a resolved-reason `title`; the trigger carries `aria-invalid` when the current value is unsupported — the exact contract the truthfulness e2e asserts. **Seeding is reconciled onto the active source, but ONLY where nothing was stored** (`seededAxisSelection(axes, {resolution, framerate})`): an axis the operator actually saved is passed through untouched and keeps flagging + blocking save when the current source can't deliver it (a stale explicit choice is theirs to re-decide, never ours to rewrite — `EncoderDialog.coherence.test.ts` pins this), while an axis with NO stored value snaps its hardcoded 1080p/30 fallback onto what the source can drive, stepping DOWN the ladder before up. That reconciliation now only bites when the source's ceiling sits BELOW the fallback (a receiver locked to 480p25, a device that tops out at 720p) — otherwise the dialog opens already-invalid: red control, save blocked, before the operator has touched anything. A 59.94-only receiver no longer triggers it, because a single reported mode is a ceiling and 30 fps is genuinely on offer (see the next bullet).
- A source's reported signal is a CEILING, not an enumeration [EXISTS]: `ValidationAdapter.ts` splits SOURCE SIGNAL from ENCODE TARGET. `singleModeSourceCeiling(modes)` returns a `SourceModeCeiling` when a source's modes collapse to exactly ONE rung on BOTH axes; `capOfferedToSourceCeiling` then keeps every resolution/framerate AT OR BELOW it and leaves everything above disabled-with-reason. Both `offeredAxes` overloads route through the shared `axesFromResolvedModes` tail, so the pipeline-keyed and source-keyed paths cannot drift. WHY: cerastream's DV-timings projection collapses the onboard RK3588 HDMI-RX to whatever is on the cable — verified on the board, `list-devices` returns a single cap `1920x1080 @ 60000/1001` for `/dev/video0` (`rk_hdmirx`) — and intersecting the encode target with that one mode disabled every lower rung, even though the capture leg downscales and rate-converts freely (`videoscale`/`videorate` are wired in both cerastream's generic capture-leg builder and its RK3588 template). A single-mode source therefore sets `deviceModes: undefined` (one mode applies uniformly, so there is no per-resolution refinement left to make) while a source that ENUMERATES a menu keeps the exact per-mode narrowing through `intersectCaps` — the same RØDE HDMI-to-USB-C adapter enumerates ~11 distinct resolutions, and its per-rung rate list carries genuine information. `singleModeSourceCeiling` is fail-closed: a modeless source, and a mode list whose rungs do not normalize onto the ladder, both return `undefined`, so a noisy payload can never WIDEN the offering. `axisCeiling()` is unchanged — for a single-signal source both axes were capped at that one mode, so the coarse independent-axes ceiling is still exactly the reported signal.
- **UVC mode-commanding is ACTIVE, and it is why UVC keeps exact per-mode narrowing [SOURCE-CONFIRMED]**: an earlier draft of this note asked whether a UVC capture leg negotiates a commanded mode or just reports whatever the device defaulted to. **That question is answered: it commands.** The full traced chain, one hop per repo — (1) CeraUI sends `input_id` + `resolution` + `framerate` in the engine `start` request (`apps/backend/src/modules/streaming/cerastream-backend.ts:938-950`); (2) cerastream copies them into `InputKind::UvcH264`/`UvcH265` (`cerastream/crates/cerastream/src/engine/capture.rs:73-99,120-127`); (3) `SourceSpec` emits `libuvch264src ! capsfilter` carrying those EXACT dimensions/framerate (`cerastream/crates/cerastream-core/src/sources/spec.rs:177-217`, built by `h264_caps`/`h265_caps` at `:373-413`); (4) the plugin intersects that capsfilter against the device's OWN enumerated UVC format descriptors and calls `uvc_get_stream_ctrl_format_size(...width,height,framerate)` (`gstlibuvch264src/libuvch264src/src/gstlibuvch264src.c:455-541,588`); (5) the libuvc fork issues a UVC `SET_CUR` that actually commands the hardware (`libuvc/src/stream.c:415`). With no override the plugin auto-selects "the highest compatible resolution, at the highest supported framerate" (`gstlibuvch264src.c:463`) — still a negotiation, not a passive read. **So the capsfilter IS the device negotiation, and that VALIDATES the current design rather than asking to change it:** because an encode target must be one of the device's ENUMERATED modes for UVC to negotiate it at all, and because there is no `videoscale`/`videorate` normalizing an uncontrolled capture in front of that negotiation (the safety net the HDMI ceiling model relies on), arbitrary downscale-below-ceiling would offer targets that cannot be selected. Exact per-mode narrowing is the truthful offering for UVC. Do NOT collapse the multi-mode branch to a ceiling.
- **Known follow-up — live mid-session UVC mode change (NOT implemented; documented deliberately)**: what remains genuinely open is not *whether* a mode can be commanded, but *when*. **A UVC mode change is a STREAM RESTART, not a hot property update.** libuvc refuses outright to retune a running stream — `uvc_stream_ctrl` returns `UVC_ERROR_BUSY` when `strmh->running`, carrying the upstream `@todo Allow the stream to be modified without restarting the stream` (`libuvc/src/stream.c:411-413`) — and the plugin's own reconnect path is correspondingly a full teardown/rebuild: `uvc_stop_streaming` → `uvc_close` → `uvc_unref_device` → reopen → re-negotiate `uvc_get_stream_ctrl_format_size` → `uvc_start_streaming` (`gstlibuvch264src/libuvch264src/src/gstlibuvch264src.c:1244-1268,1332,1363`). Two pieces of work follow, and neither exists yet: **(a) a stop/rebuild/restart UX flow** — CeraUI has no affordance for an operator to change a UVC capture mode mid-session with correct restart semantics *communicated*: the brief interruption, the settling delay, and the fact that the stream drops and returns must be shown honestly rather than presented as an instant switch. **(b) hardware validation across representative UVC devices** — real-camera switch latency, settling-frame behaviour after re-negotiation, and whether every advertised mode on every camera actually succeeds are all unmeasured in this repo; that needs physical cameras, not source tracing. The design direction the product wants explored remains genuinely DIFFERENT control semantics per source kind (HDMI-RX: passive single-mode receiver, ceiling-only; UVC: commandable multi-mode camera with restart-gated switching), NOT one uniform rule stretched over both. Treat UX quality as a first-class requirement alongside correctness: the operator should never be shown a rung the device cannot deliver, nor be denied one it can, nor be surprised by an unannounced stream drop.
- **A device's per-media-type ladders are DISJOINT, and the axes must not union them (device-quality-wave2) [EXISTS]**: a capture device enumerates its formats PER media type, and `groupDeviceCaps()` (`apps/backend/src/modules/streaming/capabilities.ts`) has always kept them apart — it keys on `width × height × media_type`, and `media_type` rides `DeviceMode` all the way to the frontend. `ValidationAdapter.ts` was the ONLY layer collapsing them: `deviceModeFrameratesAtResolution()` filtered modes by normalized resolution alone, so `framerateOptionsForResolution()` and `axisCeiling()` answered with the UNION of every format's rates at that rung. A camera advertising 1080p@[30,60] as `image/jpeg` and 1080p@[30] as `video/x-h264` therefore offered 60 fps at 1080p to an H.264 capture that cannot deliver it — and, with 2160p reachable only as MJPEG, told the operator the device drives 4K but not 1080p60, a pairing no single capture format can honour. Which ladder applies is NOT a guess: the active source's `kind` is what cerastream resolves into its `InputKind`, and that InputKind emits the `capsfilter` media type the UVC/v4l2 negotiation runs against (the same chain the UVC mode-commanding note above traces), so the kind NAMES the governing media type. `activeMediaTypeForModes(modes, kind)` resolves it — reusing the shared `mediaTypeToSourceKind` from `@ceraui/rpc` so the taxonomy stays single-sourced, with `image/jpeg`→`mjpeg` the one token that helper leaves unclassified — `scopeModesToMediaType()` narrows the list, and `resolveActiveMediaType()` mirrors `resolveDeviceModes` (source-keyed; the legacy `device_modes` overload was retired in device-quality-wave3 todo 11 — see the next bullet). The resolved format rides `OfferedAxes.activeMediaType`; `deviceModes` is already scoped to it, and `deviceModeFrameratesAtResolution`/`framerateAvailableAt`/`axisCeiling` re-apply it so a manually-constructed axes object is covered too. `deriveCapabilitySummary` (`lib/streaming/sourceSummary.ts`) scopes the same way, so the "SOURCE MAX" chip and the EncoderDialog `axis-device-max` line agree. **Three fail-open guards are load-bearing**, all following this file's none-cap policy that an unknown never subtracts: fewer than two distinct advertised media types narrows NOTHING (so every untagged old-engine payload is byte-identical — asserted by reference identity on `axes.deviceModes`), a kind naming none of the advertised formats narrows nothing (never narrow on a guess), and an UNTAGGED mode always counts (it carries no format constraint, so it cannot be shown to belong to another ladder).
